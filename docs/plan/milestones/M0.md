# M0 · Local preview, image delivery, and VPS acceptance

> **English — single source of truth** · [中文](M0_zh.md)

Agreed implementation plan, not an implementation report. Status is maintained in the [roadmap](../roadmap.md).

## 1. Goal and scope

Deliver the complete chain: local Compose build and preview → automated CI → tagged multi-platform image release → VPS image pull → web onboarding and real-data access → backup and restore.

Local development supports automated testing and optional UI inspection. Formal manual acceptance happens on the VPS; the user is not required to walk through every task locally.

Confirmed choices:

- React/TypeScript frontend and Python/FastAPI backend.
- Single administrator, web onboarding, and English/Chinese UI.
- Persistent SQLite for MateScope-owned data; a dedicated read-only PostgreSQL account for TeslaMate history.
- Synthetic PostgreSQL locally, exercising the same SQL adapter as production.
- MQTT/SMTP configuration and connection validation in M0.
- Version-tag-triggered image releases for `linux/amd64` and `linux/arm64`.
- The user pulls a selected image and starts it on the VPS. CI/CD validates and delivers images; it does not automatically SSH into production.

Real-time dashboards, notification rules, advanced statistics, complete PWA installation/offline behavior, and changes to the owner's existing installer remain outside M0.

## 2. Application and data contracts

### Technology and persistence

- Frontend: React 19, TypeScript, Vite, Mantine, React Router, TanStack Query, and react-i18next.
- Maps: Leaflet 1.9 with React Leaflet 5, loaded on demand. Introduce Recharts when statistical charts are actually implemented.
- Backend: Python 3.13, FastAPI, Pydantic Settings; SQLAlchemy 2 and Alembic for SQLite.
- TeslaMate adapter: psycopg 3 synchronous connection pool and parameterized SQL. Run blocking work in synchronous endpoints or worker threads.
- Tooling: uv, pnpm, Node 22. Pin compatible stable dependency releases and commit lockfiles.
- Export OpenAPI; generate frontend types/client integration with openapi-typescript and openapi-fetch. CI checks generated artifacts for drift.
- One non-root container serves the API and compiled frontend with one application process.

Environment variables control port, public URL, trusted proxy settings, and data directory. Web-managed PostgreSQL/MQTT/SMTP credentials and display preferences belong in SQLite, not generated Compose files.

Persist SQLite and the automatically generated encryption key under `/app/data`. Encrypt connection passwords at rest using cryptography; restrict key-file permissions. APIs never return saved passwords; editing supports retaining, replacing, or clearing them.

Startup migrates only MateScope SQLite. Unconfigured or unavailable PostgreSQL must not prevent login, settings, or onboarding from working.

### Onboarding and authentication

The web flow is:

1. Create administrator: username, password, confirmation.
2. Set language and display timezone, initially suggested from the browser.
3. Configure PostgreSQL host, port, database, read-only user/password, and TLS; test connection, permissions, and required schema.
4. Optionally configure MQTT authentication, TLS, and topic prefix; test connection/subscription.
5. Optionally configure SMTP authentication, TLS, sender, and explicitly send a test message to a chosen recipient.
6. Show successful, unverified, failed, and skipped settings; enter the application.

When no administrator exists, show the creation page directly, without a setup code. A database transaction ensures only one concurrent creation succeeds. Afterwards the public creation endpoint is closed and all subsequent settings require login. Document that the first person completing setup owns the instance.

Persist saved progress across refreshes, logout, and restart. Missing database credentials must not block completing onboarding. Settings expose the same editing/testing capabilities afterwards.

Saving and testing are separate. A failed test never appears successful. MQTT subscription success and the absence of new messages are distinct outcomes.

PostgreSQL help explains how to locate existing Compose/installer credentials, use Docker service names rather than localhost, and create a dedicated read-only role with a separate preparation script. Never store the database administrator credentials in MateScope or reset existing PostgreSQL passwords automatically.

Use Argon2id and server-side sessions with HttpOnly, SameSite=Lax cookies. Enable Secure for production HTTPS; explicitly disable it for local HTTP preview. Session lifetime defaults to 30 days. Logout invalidates the session; password change or CLI reset revokes existing sessions. Validate CSRF for writes and rate-limit login. No public registration, additional users, or email password recovery in M0.

### API and queries

Business API prefix: `/api/v1`.

| Group | M0 capabilities |
| --- | --- |
| Setup/auth | Setup status, first administrator, complete onboarding, login/logout, current user, change password |
| Settings | Read/update preferences; save, disable, and test PostgreSQL/MQTT/SMTP |
| Vehicles | Vehicle identifiers, names, and models |
| Trips | Vehicle/time-filtered list, individual summary and trajectory |
| Charges | Vehicle/time-filtered list and individual summary |
| Operations | Minimal liveness, application readiness, authenticated data-source diagnostics |

Lists default to the last 30 days and 50 items, with a maximum of 100. Use time-plus-ID cursor pagination; limit each query window to 90 days. Older history remains accessible through another window.

Use UTC ISO 8601 timestamps and explicit km, km/h, and kWh units. Render time in the configured timezone. Missing data stays null. Show existing trip and charging summaries without deriving energy consumption, battery health, or costs in M0.

Read only required fields from `cars`, `drives`, `charging_processes`, and `positions`. Validate actual schema capabilities, not assumed version compatibility. The application role must not read credential tables; superusers and accounts with evident business-table write privileges are not acceptable data sources.

Use at most three PostgreSQL connections and a five-second SQL timeout. Return at most 2,000 trajectory points, ordered by time with endpoints preserved; indicate simplification and do not connect across missing-coordinate segments.

Make the tile URL configurable. Default to OpenStreetMap standard tiles with attribution and no offline prefetch. Tile failure must not block trip summaries. Automated tests use fixed local tile responses.

## 3. Local Compose and CI/CD

### Local preview

Provide:

- `compose.yaml`: shared application configuration, health checks, persistence.
- `compose.dev.yaml`: source build plus synthetic PostgreSQL, test MQTT, and a local mail receiver.
- `compose.prod.yaml`: published image plus attachment to the selected existing TeslaMate Docker network.

Planned preview command:

```bash
docker compose -f compose.yaml -f compose.dev.yaml up --build -d
```

Serve the real compiled frontend and same-origin API at `http://localhost:8000`, with a configurable port. No host frontend development server is required.

Include two synthetic vehicles, recent trips/charges, empty results, missing fields, and a long trajectory. Label synthetic data clearly and document development connection values for onboarding. Seed only the development database; runtime access uses its read-only role.

Isolate development project names, data directories, and networks. Do not hardcode globally unique container names. Do not expose PostgreSQL on a host port by default; bind published local services to loopback. Document directory preparation and verify non-root write access. Ordinary shutdown preserves data; reset is a separate operation limited to explicitly identified development data.

Local, CI, and release builds share one Dockerfile. The runtime image contains neither source mounts, development servers, nor a test database.

### Continuous integration

Branch pushes and PRs targeting main run CI; ordinary CI does not publish images.

Required checks:

- Backend Ruff, mypy, and pytest.
- Frontend lint, TypeScript, Vitest, and production build.
- OpenAPI/type synchronization.
- Synthetic PostgreSQL integration and read-only permission tests.
- Local MQTT/SMTP integration tests.
- Compose validation, image build, and actual container startup.
- Playwright desktop/mobile flows: onboarding, login, connection settings, trips/charges, map, logout.
- Persistence after container recreation and backup/restore.

Store test reports, failure screenshots, and sanitized container logs as artifacts. Tests must not require production credentials, real records, or outgoing real email. Use local tile fixtures so CI does not depend on a public map service.

Ordinary branch/PR CI runs the full application checks on amd64. Release CI also starts both amd64 and arm64 images and tests critical operations on each platform, rather than only compiling them.

### Image release

Registry: `ghcr.io/t-liu93/matescope`. Publish through GitHub Actions with GITHUB_TOKEN. Grant packages:write only to publishing jobs; ordinary checks remain read-only.

| Git tag | Published image tags |
| --- | --- |
| `v0.1.0-alpha.1` | `:0.1.0-alpha.1`, plus a source-SHA traceability tag |
| `v0.1.0` | `:0.1.0`, source-SHA tag, and `:latest` |

Prereleases never move latest. M0 publishes no edge tag; ordinary main pushes do not update images.

The tag pipeline checks the actual tagged commit with the same complete check suite. Build and test both platforms; publish the version tags and multi-platform manifest only after all required checks pass.

Publish the tested image artifacts, without rebuilding another image after tests. Transfer each platform's tested image through CI artifacts, upload them in the publishing job, and assemble the multi-platform manifest.

Record source commit, version, image digest, and pull commands in the release summary. At first publication verify GHCR package visibility and VPS pull access; the intended package is publicly pullable. No production secrets or data enter image builds.

### VPS deployment and rollback

Production Compose pins a selected version or digest and joins the user-specified TeslaMate network. Add only MateScope and its own persistent data.

The bilingual runbook covers creating the read-only account, preparing the data directory/proxy, pulling and starting the image, onboarding, and real-data checks.

Before upgrading, back up MateScope and record the previous image. On failure, restore the old image; if a SQLite migration is incompatible with it, restore the pre-upgrade backup too. Do not run an old application against an incompatible new schema. Do not stop the existing TeslaMate stack with a whole-stack Compose down.

## 4. Tasks and backup

| Task | Deliverable and completion criteria |
| --- | --- |
| M0-T01 | Engineering/delivery skeleton: frontend/backend, bilingual shell, generated types, shared/development Compose, Dockerfile; localhost page works and CI builds/starts the image |
| M0-T02 | SQLite migrations, persistent key, administrator creation, sessions/account operations, authentication tests |
| M0-T03 | Onboarding/settings: steps, persisted configuration, skipping, resuming, later editing |
| M0-T04 | PostgreSQL adapter: read-only role script, diagnostics, real SQL, synthetic integration tests |
| M0-T05 | MQTT/SMTP configuration and explicit connection/subscription/test-mail checks; success and failure tests |
| M0-T06 | Vehicle/trip/charge pages, details and map; desktop/mobile usability and complete Playwright flow |
| M0-T07 | Backup/restore/reset-password CLI; configuration survives recreation and restoration |
| M0-T08 | Tag release pipeline, dual-platform runtime checks, GHCR delivery, production Compose and runbooks |
| M0-T09 | VPS acceptance: pull released image, first install, real-data comparison, persistence, upgrade/recovery walkthrough |

Proceed in this order. Compose/image checks start at T01 and remain active throughout; T08 finishes remote image delivery, and T09 validates that published artifact.

Provide `matescope backup`, `matescope restore`, and `matescope reset-password`. Backup uses SQLite's online backup API and includes the database, decryption key, and a format-version manifest, not TeslaMate history.

Write backups to an explicitly selected location with restricted permissions. They contain recoverable credentials. M0 does not schedule, upload, or expose web downloads of backups; existing VPS scripts can invoke the CLI.

Restore with the service stopped into an empty directory. Validate archive contents/version and revoke old sessions. Missing encryption keys must fail clearly, never trigger silent replacement. Test restoration against disposable data without overwriting the original directory.

Use the existing AGENTS model, review, implementation-commit, fixup, and per-step squash rules when orchestration is explicitly requested. This plan does not change review severity thresholds.

## 5. Acceptance and documentation

Before handing off to VPS acceptance, demonstrate:

- A clean development Compose launch supports the complete user flow.
- Both release architectures start and perform critical API operations.
- Concurrent initialization, unauthorized access, logout, configuration changes, and restart persistence work.
- Invalid credentials, empty data, missing columns, SQL timeouts, and insufficient/excessive permissions have clear outcomes.
- Pagination, timezone date boundaries, unfinished records, missing coordinates, and long trajectories are tested.
- Backup/restore has actually been exercised.
- The target image is pullable and traceable to its source and digest.

Concentrate the user's formal walkthrough into a complete VPS acceptance: administrator setup, connection configuration, representative trips/charges, Grafana comparison, mobile maps, restart, and backup/recovery. Record the deployed TeslaMate version and actual schema compatibility. Keep coordinates and credentials out of public reports.

CI covers application behavior and known schemas; it cannot guarantee the unknown VPS environment will require no adjustments. Record local checks, image publication, and VPS acceptance separately. All three must complete before closing M0.

Update the English/Chinese milestone and roadmap together. Development, release, deployment, and recovery documentation must be bilingual with English authoritative. Do not mark planned commands, workflows, publications, or walkthroughs as implemented.
