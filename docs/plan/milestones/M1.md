# M1 · Daily dashboard and complete-history browsing

> **English — single source of truth** · [中文](M1_zh.md)

Implementation design, not an implementation report or authorization to execute it. Progress belongs in the [roadmap](../roadmap.md). This document is usable by both human developers and orchestrated workers; it does not assign models. Follow the [agent guide](../../../AGENTS.md) when implementation is explicitly authorized.

## 1. Objective and scope

Turn the existing data-validation interface into a compact, informative daily dashboard for phones, tablets, and desktops, progressively replacing TeslaMate Grafana. M0 and the post-alpha security/PWA work are the existing foundation, not work to repeat.

### Confirmed product scope

- A concise overview combining recent known vehicle data with period summaries and recent records.
- One global selected vehicle; carry that context between pages. De-emphasize selection in single-vehicle instances. No combined-vehicle summaries in M1.
- Complete history, including multi-year and all-history selection, through a date picker rather than UTC text entry.
- Complete common trip and charging workflows, with useful list summaries, details, charts, and return-state restoration.
- Basic metrics, estimated driving energy, and existing charging costs.
- Trip speed, power, battery level, temperature, and elevation charts; charging power, battery level, and outdoor temperature charts.
- Compact modern layouts, responsive navigation, and light/dark appearance.
- PostgreSQL history and latest recorded values; no continuous MQTT ingestion.

The complete product is organized around Overview, Trips, Charges, Analysis, and Footprint. M1 exposes only Overview, Trips, and Charges in primary navigation. Do not show placeholder pages for later features.

### Non-goals

Advanced statistics, battery health, parking drain, footprint analysis, multi-drive journey summaries, a unified activity timeline, cross-vehicle aggregation, exports, charge-cost or location editing, AC/DC filtering, notification rules, live MQTT, vehicle control, PWA reconstruction, offline vehicle browsing, and scroll-performance optimization are excluded. Do not modify TeslaMate data, schema, or indexes, the Linux Install Helper, or any existing production service.

This milestone does not itself authorize access to a VPS, real PostgreSQL, home MQTT, or real SMTP; publishing and production deployment are separate actions. Use only isolated synthetic services for development and tests.

### Baseline and specification choices

The implementation baseline is `v0.1.0-alpha.2`, source `646fdf82d2fdde7a46d7199e51b8bd01be8d926a`. Recheck the worktree before implementation and preserve subsequent changes. The previous walkthrough containers, volumes, networks, and local MateScope images are not assumed to exist.

Upstream research is pinned to TeslaMate `c187d0269a31bcaa1497678469e3836ef9a260da`: [dashboard definitions](https://github.com/teslamate-org/teslamate/tree/c187d0269a31bcaa1497678469e3836ef9a260da/grafana/dashboards). MateScope's current “trip” is one upstream Drive; upstream Trip combines several drives and charges over a period and remains outside M1. Use upstream queries to understand fields, not as SQL to copy without adapting permissions, bounds, and missing-data rules.

Defaults below—such as 50-row pages, rated range, 600 chart buckets, and layout breakpoints—are design choices, not claims of individually confirmed user preferences or verified production behavior. They are the implementation defaults for this plan; any later revision must update both language versions before dependent work. Runtime currency is deliberately unset until the owner selects it. Production schema compatibility, native-device acceptance, and deployment outcomes remain unverified; no task may describe them as passed in advance.

## 2. Pages and workflows

### Application shell and shared context

| Area | Required behavior |
| --- | --- |
| Primary navigation | Overview, Trips, Charges |
| Phone, below 768px | Vehicle selector and Settings at the top; three-item bottom navigation respecting the safe area |
| Tablet, 768–1199px | Side navigation and shared vehicle/page context; adapt content columns to available width |
| Desktop, 1200px and above | Side navigation; wider summaries, lists, and two-column detail sections |
| Settings | Preserve current connection, password, 2FA, onboarding, and logout behavior; add display preferences |
| Vehicle selection | Explicit URL selection wins; otherwise retain the current in-memory selection, then use the lowest available vehicle ID |
| Empty/invalid selection | Zero vehicles shows an empty state and settings link; an unavailable URL-selected vehicle shows a clear selection prompt rather than silently showing another car |
| Appearance | System default, with light/dark overrides; only non-sensitive UI preferences may be stored in Web Storage |
| Existing routes | Keep `/vehicles`, `/trips/:id`, and `/charges/:id` working; `/vehicles` is not a primary navigation item |

Use the existing React/Mantine stack. Add `@mantine/dates` aligned with the installed Mantine 8 version, rather than upgrading the whole UI framework. Use Recharts for charts. Add and pin compatible dependencies only in the step that introduces their use; do not add another chart library. [Mantine 8 date picker](https://v8.mantine.dev/dates/date-picker-input/), [Recharts](https://recharts.github.io/en-US/api/LineChart/).

Keep vehicle records, names, locations, summaries, and charts in online memory only. URLs may contain vehicle/record identifiers, resolved time bounds, and pagination context, but not record contents or location names. Direct detail navigation must show the record's owning vehicle in the shell, even if another vehicle was previously selected.

### Overview

Exactly three content areas:

1. **Latest recorded values:** battery level, selected-basis range, odometer, and their source timestamps.
2. **Selected-period summary:** driving distance, estimated driving energy, energy added by charging, and recorded charging cost. Use two columns on phones and at most four on desktop.
3. **Recent records in that period:** the latest three trips and three charges, each section linking to its full list.

Latest recorded values are independent of the date filter. The other two areas use the selected period. Headings make this distinction explicit. Do not add overview trend charts, gauges, state timelines, or charging-state panels.

Distance/estimated-energy links open Trips; energy-added/cost links open Charges, retaining the vehicle and period. Record links open details. A failed section does not hide working sections. Distinguish empty results, missing values, insufficient permissions, and request failure. Successful refetching must not relabel an old source sample as fresh or “live.”

### Date selection

Use a calendar range picker: modal on phones, popover on wider screens. Provide Today, Last 7 days, Last 30 days, This month, This year, All history, and Custom. Allow year/month navigation so old dates do not require repeated month-by-month clicks.

Default to the last 30 local calendar days including today. Interpret dates in the saved IANA timezone, not the browser timezone; use Monday as the calendar's first weekday. Custom end dates include that calendar day. The backend resolves them to UTC `[start, end)` bounds, capped at the resolution instant for today. Reject reversed ranges, incomplete custom selections, and future dates. Compute each calendar boundary independently across DST rather than adding fixed 24-hour durations.

Apply changes only on Apply; Cancel leaves the current query intact. Remove the UTC ISO text-entry requirement. Changing vehicle or applying a new range resets pagination. Across pages use the same resolved range until explicitly changed or refreshed; browser Back must not silently resolve a different “now.”

All history starts at the earliest trip or charge start for the selected car and ends at the resolution instant. Return an explicit empty window when there is no history; do not invent a year such as 1970 or issue a zero-width list query. For a vehicle change, re-resolve an All history preset for the new vehicle.

### Trip list

Group records by local start date, descending by start time and ID. Show start time, origin → destination, distance, duration, starting/ending battery level, and estimated energy. Desktop may additionally show estimated average consumption; phone layout must not require horizontal scrolling. Truncate long place names in the list and show them fully in details.

The period summary shows count, distance, duration, and estimated energy for the entire selection, never just the visible page. Use 50-row pages with Previous/Next, not infinite scrolling. Location search and advanced filters are excluded. Records without an end remain visible and are labeled “Record not ended,” not asserted to be a currently running drive.

### Trip detail

Order: back link and date/places; distance/duration/battery/estimated-energy summary; route map; speed/power chart; battery chart; collapsed More data containing inside/outside temperatures and elevation.

Use a vertical phone layout; on desktop put the summary and map side by side, then chart sections in two columns where space permits. Speed and power have separate labeled unit axes. Do not combine battery, temperature, and elevation into a single multi-axis chart. Keep map/individual chart failures local. Reuse current trajectory protection. No brushing, map/chart synchronization, tire pressure, or GPX export.

### Charging list and detail

The list shows time, place, starting/ending battery level, energy added, duration, and recorded cost. The period summary shows count, energy added, duration, and recorded cost. Grouping, pagination, and restoration follow Trips.

Detail order: place/time/summary; battery change, energy added, recorded energy used, cost; power/battery chart; collapsed More data with outdoor temperature. Do not infer missing energy used or introduce charging-efficiency estimates, station statistics, or cost editing.

### Navigation, privacy, and failure behavior

- Returning from a detail restores vehicle, period, page, scroll position, and keyboard focus to the triggering record. Browser Back/Forward behaves consistently. A reload restores filters/page, not necessarily an exact scroll pixel.
- Route/context state stores identifiers and navigation metadata only. Clear record caches on logout and offline transitions. Do not retain old-vehicle content while switching cars.
- New query keys must participate in the existing offline guard: windows, summaries, snapshots, and series as well as lists/details/maps. Cancel obsolete work; late responses must not republish old-car, old-window, or offline data.
- Restore connectivity by refetching. Do not mount/unmount authentication or recovery-code flows as a side effect of clearing history data.
- Preserve PWA installation, service-worker update behavior, and the prohibition on caching vehicle/API/map data. This is extension of the existing privacy boundary, not a new PWA project.

## 3. Data contracts and metric definitions

### APIs

Keep `/api/v1`, current routes, existing fields, and authenticated `no-store` responses. Add nullable fields to existing summaries. Introduce focused endpoints rather than one large dashboard response. API changes and generated TypeScript types ship together in each owning step.

| Endpoint, relative to `/api/v1` | Contract |
| --- | --- |
| `GET /vehicles/{id}/history-window` | Preset or custom local dates; returns saved timezone, resolved UTC bounds, and explicit empty-window status |
| `GET /vehicles/{id}/snapshot` | Battery level, selected-basis range, and odometer, each with its own source timestamp |
| `GET /vehicles/{id}/trip-summary` | UTC-bounded period aggregates and metric coverage counts |
| `GET /vehicles/{id}/charge-summary` | UTC-bounded aggregates, cost currency/coverage, and unavailable-data indicators |
| Existing trip list/detail | Additional place names, starting/ending battery, estimated energy, and estimated average consumption |
| Existing charge list/detail | Additional place, battery change, energy used, and cost |
| `GET /trips/{id}/series` | Speed, power, battery, inside/outside temperature, and elevation |
| `GET /charges/{id}/series` | Power, battery, and outdoor temperature |
| `GET /history/capabilities` | Availability of added capability groups and missing-permission/incompatible-schema reasons |

New summaries require a single vehicle. Existing list API behavior without a vehicle remains compatible, although M1 UI does not expose all-car aggregation. Return not-found for nonexistent vehicles/records, validation errors for invalid ranges/cursors, and classified source errors for database failures. Never substitute fixture data. Unavailable added fields/series carry explicit capability information, not indistinguishable “no records” responses. Base safety violations continue to reject the data source.

### Time and database work

Assign a trip/charge wholly to the period containing its start time: `start >= window.start AND start < window.end`. Do not split cross-midnight duration or energy. Remove the 90-day maximum while preserving strict chronological/cursor validation. Order pages by start and ID descending; bind cursors to record kind, vehicle, and resolved window.

All history is still paginated. Compute aggregates in SQL using drives/charging-process summaries and necessary car metadata, not by downloading every page or scanning all trajectory samples. Keep read-only transactions, the current connection bound, and five-second SQL timeout. A timeout is an error, never a successful truncated aggregate. Do not create TeslaMate indexes, summary tables, or background precomputation.

### Metrics

| Metric | Definition |
| --- | --- |
| Counts | Return total, ended, and not-ended record counts in the range |
| Distance/duration totals | Sum valid nonnegative values from ended records only |
| Starting/ending SOC | Original linked percentage values; missing stays null |
| Estimated trip energy | `(start range - end range) × cars.efficiency`, in kWh |
| Estimated average consumption | Sum valid estimated energy / sum distance of exactly those same records, converted to Wh/km |
| Energy added | `charge_energy_added`; never replace with charger energy used |
| Recorded energy used | `charge_energy_used`; do not fill null using energy added |
| Cost | Existing `cost`; distinguish null from explicit zero |

Energy uses the upstream range-difference/efficiency approach and is always labeled estimated. [Pinned upstream drive query](https://github.com/teslamate-org/teslamate/blob/c187d0269a31bcaa1497678469e3836ef9a260da/grafana/dashboards/drives.json).

- Add a `rated`/`ideal` range preference, default `rated`. Label the basis and use it consistently for range and energy; do not silently fall back between bases.
- Energy requires an ended record, positive distance and efficiency factor, and present finite inputs. Negative range difference makes that record's energy unavailable; exclude its distance from average-consumption denominators. Zero difference is valid zero energy.
- Charge period energy/duration/cost aggregates likewise use ended records. Individual unfinished details may show recorded values, explicitly provisional. Include not-ended counts alongside coverage.
- Every aggregate reports valid/applicable counts. Applicable means ended records for that metric; unavailable/invalid values reduce valid coverage. Empty periods yield zero counts/totals. When records exist but none qualify or all required values are missing, return null with the reason/coverage rather than a misleading zero. Undefined averages, including a zero denominator, are null.
- Preserve backend numeric precision while aggregating; round only for presentation. Never average per-trip averages. Counts are integers; distance/energy/consumption show at most one decimal, SOC whole percentages, and recorded costs two decimal places.
- Use km, km/h, kW, kWh, Wh/km, °C, and m. Imperial-unit switching is outside M1.

### Currency

TeslaMate cost values have no per-record currency. Add a nullable display-currency preference; do not infer it from language/timezone. Without it, show raw individual costs with “Currency not configured,” but no overview/period cost total. Selecting a currency means the owner confirms a common currency for those records; it does not convert amounts. Explain this in Settings. Use an uppercase three-letter currency code supported by the currency selector; unknown input is rejected. Do not aggregate mixed-currency history as if converted.

Missing costs are unknown, not free. Aggregate only present costs and label their coverage; explicit zero is a known cost. No cost editing or exchange-rate service.

### Locations and latest values

Display a nonempty geofence name first, otherwise an address name or road/house number together with city, otherwise “Unknown location.” No external reverse geocoding and no coordinates as default list labels.

For battery and selected range, independently choose the latest valid value from the car's positions and charges joined to its charging processes. Odometer comes from the latest valid position. Order tied source rows by ID; for equal timestamps across the two sources prefer the charge value. Retain each field's timestamp; do not invent a common snapshot time. No state inference from these records. Fetch on page entry and explicit refresh, with no new continuous polling.

### Series

Return named series, explicit units, UTC time bounds, original sample count, bucket count, and aggregation metadata. Each series contains at most 600 time buckets. Preserve raw timestamps for small records; use equal-width time buckets for longer ones. Continuous values expose mean/min/max; SOC exposes the last valid value. The chart displays mean/last and explains ranges/aggregation in its data description.

Empty buckets, missing samples, and gaps over five minutes must break the line. If aggregation would hide an internal missing interval, flag that bucket as a discontinuity and do not draw a connecting line through it. Preserve negative power. Do not interpolate through nulls. A missing field affects only its series. Aggregate in SQL; do not transfer unbounded samples into Python/the browser. For unfinished sessions, use available sample bounds rather than inventing a completed end.

Keep existing route sampling separate, at most 2,000 points with simplification and gap markers. Charts use the saved timezone and provide accessible text descriptions for mouse, touch, and keyboard users.

### Read-only access and compatibility

Retain M0 base checks. Diagnose additional capabilities separately so an old minimally privileged role can still use existing list fields, basic details, and maps. Missing added fields produce null plus capability information or a local unavailable section; they must not disable authentication, settings, or recovery.

The additional SELECT allowlist, beyond existing M0 columns, is limited to the following. IDs/FKs below are only for the described joins. Validate types and effective column privileges before using optional columns; do not issue a forbidden query and catch it as empty data.

| Table | Additional columns |
| --- | --- |
| `cars` | `efficiency` |
| `drives` | `start_position_id`, `end_position_id`, `start_address_id`, `end_address_id`, `start_geofence_id`, `end_geofence_id`, `start_rated_range_km`, `end_rated_range_km`, `start_ideal_range_km`, `end_ideal_range_km` |
| `charging_processes` | `address_id`, `geofence_id`, `start_battery_level`, `end_battery_level`, `charge_energy_used`, `cost` |
| `positions` | `car_id`, `odometer`, `battery_level`, `rated_battery_range_km`, `ideal_battery_range_km`, `speed`, `power`, `inside_temp`, `outside_temp`, `elevation` |
| `charges` | `id`, `charging_process_id`, `date`, `battery_level`, `rated_battery_range_km`, `ideal_battery_range_km`, `charger_power`, `outside_temp` |
| `addresses` | `id`, `name`, `road`, `house_number`, `city` |
| `geofences` | `id`, `name` |

Do not read tokens, users, VINs, or unrelated settings. Keep existing unsafe-role rejection. Use explicit SQL projections rather than `SELECT *`. Parameterize values and whitelist any dynamically selected range-column names.

Provide a separate idempotent upgrade script for an explicitly specified existing role: grant only required SELECT columns, create no role, reset no password, and revoke no unrelated grants. Update the fresh-role preparation path to grant the same required capabilities. The application never executes either script. Test both only on synthetic PostgreSQL.

Store range/currency preferences in current MateScope configuration, with defaults for old JSON. A legacy preferences update that omits new fields preserves stored new values; explicit null clears currency. Do not add a SQLite schema migration merely for JSON preferences. Old application versions may reject the added configuration fields, so rollback can require restoring a pre-upgrade backup, even without a schema migration.

## 5. Acceptance, isolation, and upgrade

### Required behavior checks

| Scenario | Expected result |
| --- | --- |
| Open overview | Concise latest values, four summary slots and recent records; no chart wall |

### Upgrade and rollback

1. Back up MateScope-owned data and record the previous image before upgrade.
2. Start the new version with the existing account; base functions must remain usable without expanded grants.
3. In a separately authorized deployment step, the owner reviews/runs the minimal read-only grants.
4. Explicitly retest the source and verify newly available capabilities.
5. Check a selected vehicle, dates, summaries, and representative details.
6. On rollback, restore the previous image; restore the pre-upgrade backup if the previous version cannot read the new configuration. Do not assume no SQLite migration means guaranteed configuration compatibility.

Preserve current restore behavior: sessions and recovery codes are invalidated as already specified, an enabled authenticator remains enabled, `reset-password` retains 2FA, and `reset-2fa` remains an explicit operator recovery action. Do not describe invalidated recovery codes as retained merely because account authentication survives restoration.

No step automatically changes production services, grants live permissions, publishes an image, or performs a live rollback. The manual walkthrough must use synthetic or separately authorized targets, with expected outcomes matching the acceptance table.
